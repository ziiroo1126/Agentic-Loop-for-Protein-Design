## 项目定位

MolClaw 是面向分子相互作用设计的科研 Agent：将研究需求转成经过校验的任务，在有限计算预算内调用生成与评估工具，依据结果选择下一步，并交付候选结构、序列和可追溯的计算证据。

第一版围绕一种 binder 设计任务完成产品与实验。保留现有 ODesign 和 evedesign 接口，
以 Python 工作流为执行核心，由宿主通过 skill 调用。第一版只接一个生成后端；
多模态设计、新基础模型训练和通用生物工具平台放入后续范围。可将候选决策交给独立
子 Agent，其输入限定为执行器提供的可见观察，保留请求、响应和已知的宿主来源。

对两类申请材料，使用同一套工作与证据，强调不同部分：

| 用途 | 项目应提供的证据 | 个人需要能解释的内容 |
| --- | --- | --- |
| AI / Agent / ML 工程求职 | 可运行演示、接口设计、长任务管理、错误恢复、自动化检查、性能记录 | 为什么这样划分组件，怎样处理工具失败，成本和延迟如何测量 |
| AI for Science / 计算方向 PhD | 明确问题、相关工作、基线、受控实验、消融、失败分析与技术报告 | 假设是什么，实验能支持什么，增益来自哪里，哪些结论仍不成立 |

这是建议的展示重点，不代表所有岗位或 PhD 项目使用相同标准。CMU 的申请建议强调说明研究问题、重要性、技术方案和验证过程，可作为组织研究叙事的参考。[CMU 教师的申请建议](https://www.cs.cmu.edu/~aldrich/essay-advice.html)

## 用户可见的最终成果

一个完整案例应支持如下流程：

1. 用户提供目标结构、希望结合的区域、binder 长度等约束和计算预算。
2. Agent 生成结构化任务，显示采用的假设，询问阻止执行的缺失信息。
3. 系统运行生成和评估，展示进度、计算消耗与中间结果。
4. Agent 根据工具返回的结构化观察选择下一步；执行层校验每一步是否符合约束和预算。
5. 用户比较候选结构、各项评分、通过条件与淘汰理由，导出序列、结构和完整运行记录。

第一版在宿主会话中呈现任务定义、运行轨迹和候选比较，输出可打开的结构与报告。
每条推荐关联候选与指标。离线演示使用真实运行的历史记录并标注为回放；mock 只用于工程测试。
可视化结果页可作为后续补充，不承担独立模型编排服务。

首个真实推理检查继续使用现有 `examples/real_smoke_ligand_binder.json`。后续研究任务可选择目标蛋白到小型蛋白 binder 的场景，但需先验证输入映射、评估器适用性和可用任务数据。蛋白—蛋白和蛋白—小分子任务的评估协议分别制定，不共用未经验证的阈值。

## Agent 的实现范围

Agent 负责提出计划、解释观察、选择允许的动作和形成结果说明。执行层负责参数校验、任务状态、进程管理、预算约束和产物记录。

建议提供的工具能力：

| 能力 | 输入与输出边界 |
| --- | --- |
| 校验任务 | 结构化任务 → 校验结果、缺失条件及解析后的约束 |
| 提交生成 | 已校验任务与采样配置 → job ID；后台执行真实模型 |
| 查询或取消任务 | job ID → 状态、日志位置、产物与已用预算 |
| 评估已有候选 | candidate ID 与评估协议 → 持久化评估任务及指标 |
| 比较与导出 | 已评估候选与预设筛选规则 → 排序、多样性摘要和报告 |

工具与底层 CLI/API 共用实现。Agent 采用的 LLM、提示词和工具定义记录版本；先固定一个 LLM 完成实验。用户设定的硬约束与筛选标准在一次实验中保持不变，允许改变的设计参数单独列出。

## 研究问题与贡献边界

建议的主问题：在相同生成模型、工具、硬约束与计算预算下，依据结构化评估反馈选择后续生成或评估动作，能否提高满足预设条件的多样候选产出？

先研究一个具体机制：每轮汇总约束违反、候选重复程度和评估结果，Agent 在预先规定的动作空间内选择追加采样、进一步评估或停止。成本由执行层计量，硬约束由代码校验。观察到的指标与原因解释分别保存，避免把推测当成工具证据。

这是一项待验证假设。集成、接口、网页和日志属于工程贡献；方法贡献需要证明决策机制相对基线的作用。

与已有工作的边界：

- [evedesign](https://github.com/evedesignbio/evedesign) 已提供统一分子设计接口；应说明本项目使用并扩展它的哪些边界。
- [ODesign-pipeline](https://github.com/OTeam-AI4S/ODesign-pipeline) 已连接生成与 AF3/PyRosetta 筛选；这条工具组合归于上游。
- [AutoBinder Agent](https://arxiv.org/abs/2602.00019) 已研究 LLM/MCP 协调 binder 设计；“使用 Agent 做 binder 设计”本身不足以证明新颖性。
- [BioDesignBench](https://www.biorxiv.org/content/10.64898/2026.05.06.723381v1) 研究了蛋白设计 Agent 的评估深度与探索行为，可帮助定义失败模式和比较对象。
- [ProtDBench](https://arxiv.org/abs/2605.04118) 已讨论预算、结构多样性及评估器偏差；使用这些指标是实验设计基础，不能直接当作本项目首创。

## 实验方案

先完成少量开发任务的计时试验，再根据实际吞吐确定独立测试目标数与每个方法的重复次数。开发目标与测试目标分离，同一目标的不同提示词或随机种子不作为独立目标计数。

| 对照 | 目的 |
| --- | --- |
| 固定流程与固定预算分配 | 检查 Agent 是否比预设工作流有效 |
| 通用工具调用 Agent | 检查结构化反馈和动作约束是否带来增益 |
| 不依赖 LLM 的反馈启发式策略 | 检查同样的反馈是否可以通过更简单的策略利用 |
| MolClaw 的完整策略 | 检验主假设 |

比较时固定生成与评估工具、模型版本、硬约束、初始输入、停止规则和资源上限。LLM 方法尽量使用相同底座模型。生成与评估均计入 GPU 预算，另记录 CPU 时间、总耗时、LLM token 和 API 费用。报告候选、任务和目标三个层次的计数，避免将大量相关候选当成大量独立实验。

主要记录：

- 工程结果：任务完成率、恢复成功情况、无效调用、重复计算、超预算事件。
- 计算筛选结果：硬约束满足率、通过筛选的候选数及结构簇数。
- 效率：每 GPU 小时的通过筛选候选数、达到首个通过候选的成本。
- 决策行为：生成与评估的分配、候选比较次数、终止原因。
- 验证边界：独立评估结果、不同评估器的一致性，以及可以获得时的实验数据。

最小消融比较使用评估反馈和不使用反馈的策略，保持动作空间及预算相同；后续再分别分析多样性信息和约束诊断的作用。报告逐目标结果与重复运行的变化。小样本结果标注为探索性证据，避免预先承诺显著性或性能提升。

计算筛选通过与真实结合、选择性、功能分开表述。没有湿实验时，结论限定为计算工作流性能和所用评估协议下的候选质量。

## 里程碑与验收

按可检查的成果推进；真实计算耗时与预算通过第一阶段测量后再排期。

| 阶段 | 交付物 | 验收标准 |
| --- | --- | --- |
| M1：真实流程基础 | 修复记录与排序问题，独立评估入口，一次真实生成与评估 | 真实结构、序列和评估产物齐全；故障也保留记录；恢复评估不重新生成 |
| M2：Agent 工具循环 | 结构化工具、状态持久化、预算控制、反馈决策 | 至少一个完整案例有真实执行轨迹；验证缺失输入、工具失败、取消和预算用尽的行为 |
| M3：可演示项目 | 宿主 skill/插件、文档、3–5 分钟视频与真实记录回放 | 第三方能按文档加载适配包、启动示例、比较候选并定位原始证据 |
| M4：研究证据 | 冻结实验协议、基线、消融、逐目标结果与技术报告 | 从运行记录可重建结果表；说明方法贡献、失败案例和结论边界 |
| M5：申请材料 | 中英文简历条目、项目说明、架构讲解与贡献清单 | 每条成果可链接到代码或实验记录；本人贡献和上游能力归属准确 |

M3 完成后可作为具备真实执行证据的工程项目展示；M4 增加支持研究叙事的证据。是否投稿以及投向何处，由实际结果与相关工作比较决定。

## 个人贡献与简历写法

保留一份贡献清单，逐项记录问题、本人决策、代码/实验位置、验证方式和结果。BioClaw、evedesign、ODesign 及评估工具的能力明确注明来源。能够解释依赖选择、接口权衡、失败原因和实验结论，是项目展示的重要组成部分。

下面仅是完成后使用的模板，方括号必须替换为真实测量值；未完成时使用“正在开发”等准确时态：

**工程方向**

> 基于 evedesign 与 ODesign 开发分子设计 Agent，负责 [实际负责模块]，实现结构化工具调用、持久化任务状态、预算约束及结果追溯；在 [N] 项测试任务中测得 [指标及数值]，提供可复现运行和交互演示。

**研究方向**

> 研究评估反馈对有限预算分子设计的影响，设计 [具体决策机制]，在 [N] 个独立目标上与固定流程、通用 Agent 和反馈启发式进行比较；通过 [消融设置] 分析 [发现]，在 [明确评估协议] 下得到 [实际结果]。

即使没有稳定超过基线，若实验充分揭示了策略失效条件、工具瓶颈或评估偏差，也应如实记录。这些发现可用于技术报告和研究交流，不预先写成正向提升。
